Backend Plan: Demo Accounts Seeding

Repo: D:\Projects\Code\Personal\BatchVault\BatchVault_Back. Date: 2026-06-03.

Task Summary

Add an explicit manual operation that creates screenshot/demo accounts for English, Serbian, and Russian demos. The operation must populate realistic product data without becoming part of normal application startup, registration, migration, or deployment behavior.

Current Behavior

  • POST /api/auth/register creates a user and calls database.EnsurePersonalWorkspaceForUser.
  • database.ConnectDatabase() runs migrations and backfills on every application start.
  • There is no dedicated seed command for demo accounts or localized demo content.
  • Operational records are scoped by workspace_id where migrated and still carry user_id for legacy compatibility.
  • The repository has an English-only rule for code, comments, documentation, API messages, and normal committed text.

Desired Behavior

  • Create three manual demo identities: demo-en, demo-sr, and demo-ru.
  • Each identity gets its own personal workspace through the existing workspace helper, not through hand-built workspace rows.
  • Each workspace gets a coherent data story: ingredients, workspace ingredient metadata, prices, recipes, recipe ingredients, packages, products, clients, orders, and cooking sessions.
  • The command is idempotent for demo users: re-running it replaces only the data owned by those demo accounts.
  • The demo dataset has an explicit version and can be refreshed when new product features need additional demo records.
  • The command never runs automatically from main.go, database.ConnectDatabase(), Docker startup, or CI.
  • Localized Russian and Serbian fixture values are allowed only inside this manual demo seeding feature, based on explicit user approval for demo account content.

Refresh and Evolution Model

  • Treat demo content as a maintained fixture package, not a one-off migration.
  • Store a demo dataset version, for example demo_dataset_version = "2026-06-03.1", in the seed code and in a small marker row or metadata record tied to each demo workspace.
  • Support a normal refresh mode that reconciles demo accounts to the current fixture version.
  • Support a stricter reset mode that deletes and recreates all records owned by the demo accounts.
  • When a new feature is added, update the fixture model and bump the dataset version so operators can rerun the command and get the new demo surface.
  • Keep stable demo usernames and passwords so screenshots, app-store review notes, and shared demo instructions do not change every time fixtures are refreshed.
  • Prefer deterministic fixture keys such as slugs or stable names for demo records so refresh logic can update existing demo rows instead of creating duplicates.

Assumptions

  • The first implementation can use fixed demo passwords supplied by environment variables, with documented local defaults only if approved.
  • The seed target is a development, staging, or demo database, not a normal production tenant database unless explicitly run by the operator.
  • The demo datasets should be similar in structure across languages so screenshots are comparable.
  • The backend remains responsible for database records; frontend locale switching remains responsible for UI labels and navigation text.

Safety Model

  • Require DEMO_SEED_CONFIRM=seed-demo-accounts before making changes.
  • Require DATABASE_URL just like the application.
  • Refuse to run if a target username does not start with demo-.
  • Delete and recreate only records reachable from the selected demo user IDs and their personal workspaces.
  • In refresh mode, update demo-owned records by stable fixture keys and avoid touching non-demo records.
  • In reset mode, require an additional explicit flag such as DEMO_SEED_MODE=reset.
  • Print a summary of created usernames and record counts; do not print password hashes or database credentials.

Likely File Changes

  • cmd/seed_demo_accounts/main.go: command entrypoint, env validation, transaction orchestration.
  • internal/demo_seed/ or database/demo_seed.go: reusable seed helpers if the command becomes large.
  • internal/demo_seed/fixtures.go: fixture definitions, including localized demo values.
  • internal/demo_seed/version.go: current dataset version and refresh/reset mode constants.
  • internal/demo_seed/demo_seed_test.go: idempotency and scoping tests.
  • README.md or a short docs file: manual operator instructions, only after implementation is approved.

Implementation Steps

  1. Add a manual Go command under cmd/seed_demo_accounts.
  2. Open the database with the same GORM/Postgres stack used by the app, but avoid invoking normal server startup.
  3. Run required migrations through existing connection code only if that does not create unwanted side effects; otherwise factor a shared migration helper before seeding.
  4. Define demo account fixtures for English, Serbian, and Russian, including username, workspace name, ingredients, recipes, products, clients, orders, and dates.
  5. Define stable fixture keys for every seeded entity that may need refresh updates later.
  6. Hash passwords with utils.HashPassword.
  7. Create users inside transactions and call database.EnsurePersonalWorkspaceForUser.
  8. Insert workspace-scoped and user-scoped records consistently, including workspace_id on migrated business tables.
  9. Add refresh logic that upserts current fixtures for demo accounts and removes obsolete demo-owned fixture rows when safe.
  10. Add reset cleanup logic that removes only previous demo-* records before reseeding.
  11. Add focused tests using an isolated test database or sqlite-compatible GORM path if the existing test pattern supports it.

Test Plan

  • go test ./internal/demo_seed ./database ./models if seed helpers live under internal/demo_seed.
  • go test ./... to catch model and controller regressions.
  • Manual local dry run against a disposable database.
  • Run the command twice and verify that demo record counts do not duplicate.
  • Change the fixture version in a test fixture and verify refresh updates existing demo rows predictably.
  • Run reset mode and verify it recreates only demo-owned records.
  • Login as each demo account and verify GET /api/workspaces/current, dashboard, recipes, ingredients, prices, products, clients, and orders return populated data.

Manual QA Checklist

  • English account screenshots show natural English business data.
  • Serbian account screenshots show natural Serbian business data where demo data is user-entered content.
  • Russian account screenshots show natural Russian business data where demo data is user-entered content.
  • Frontend UI language is verified separately through frontend locale settings.
  • After a fixture version bump, rerun refresh mode and verify new feature data appears in all three demo accounts.
  • No non-demo users or workspaces are modified by a repeated seed run.

Risks

  • Cleanup order can violate foreign keys if relationships are deleted in the wrong sequence.
  • Global ingredients are currently name-unique, so localized ingredient names may create shared global rows that outlive demo cleanup.
  • Refresh logic can become fragile if fixtures rely only on translated display names instead of stable keys.
  • Deleting obsolete demo records must respect relationships, otherwise historical demo screens may lose related rows unexpectedly.
  • Russian and Serbian fixture text violates the normal English-only repository rule unless explicitly limited to this approved demo seed path.
  • Running against the wrong database could overwrite existing demo accounts with the same usernames.

Rollback Plan

  • Run a cleanup mode that removes only demo-en, demo-sr, and demo-ru owned records.
  • If a refresh version is bad, revert the fixture change and rerun refresh mode against the previous dataset version.
  • If the command has not been run, rollback is just reverting the code changes.
  • If a disposable database was used for screenshots, discard and recreate that database.

Open Questions

  • Should demo passwords be fixed and documented locally, or always supplied through env variables?
  • Should fixture data live in Go source for simplicity, or in separate JSON files for easier copy editing?
  • Should this seed a local database only, or also be runnable against the live demo environment?
  • How large should each dataset be for screenshots: minimal clean data, or a fuller dashboard with history?

Known Limitations

  • Refresh mode intentionally replaces demo-owned operational rows rather than doing per-row partial merges; this keeps fixture updates predictable as features evolve.
  • Global ingredient rows are name-unique and are not deleted during demo cleanup, so old renamed demo ingredients may remain as inactive global reference data.
  • The default demo password is suitable for controlled demo environments only; shared or public environments should override passwords with env vars.
  • Live validation was performed only against the dev compose test database, not against production.
