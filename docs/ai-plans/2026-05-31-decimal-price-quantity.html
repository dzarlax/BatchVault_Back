Implementation Plan: Decimal Price Quantity

Approval required before implementation

Task Summary

Allow backend price entries to store and calculate non-integer purchase quantities, such as 2.5 kg or 0.5 l. This supports the mobile price-entry update planned in the sibling mobile repository.

Current Behavior

  • models/price.go defines PriceCreateDTO.Quantity int and Price.Quantity int.
  • controllers/prices.go copies the integer quantity directly into new price rows.
  • utils/calculateIngredientCost.go accepts priceQuantity int and converts it to float only inside the calculation.
  • database.ConnectDatabase() runs AutoMigrate, indexes, and manual backfills at startup, but no guarded quantity type migration exists.
  • Swagger currently documents models.PriceCreateDTO.quantity and models.Price.quantity as integer fields.

Desired Behavior

  • POST /api/prices accepts decimal JSON numbers for quantity.
  • Stored price rows preserve decimal quantity values.
  • Recipe cost calculation handles decimal price quantities while keeping existing mass, volume, and count conversion behavior.
  • Existing integer rows continue to work and serialize as JSON numbers.
  • Workspace scoping, strict ingredient membership validation, and deterministic latest-price ordering stay unchanged.

Files Likely to Change

  • models/price.go - switch price quantity fields to decimal-capable type.
  • utils/calculateIngredientCost.go and utils/calculateIngredientCost_test.go - accept and test decimal price quantity.
  • controllers/workspace_price_test.go and controllers/workspace_ingredients_test.go - update helpers and add decimal create/read coverage.
  • database/database.go or a new database helper - guarded PostgreSQL column type migration for prices.quantity.
  • docs/docs.go, docs/swagger.json, and docs/swagger.yaml - regenerate Swagger after model changes.
  • docs/ai-plans/2026-05-31-decimal-price-quantity.html - update after implementation.

Implementation Steps

  1. Add tests that prove decimal price quantity can be created and used in recipe cost calculation.
  2. Change PriceCreateDTO.Quantity and Price.Quantity from int to float64.
  3. Change CalculateIngredientCost to accept priceQuantity float64 and keep the same validation semantics for values less than or equal to zero.
  4. Add a startup migration that changes existing PostgreSQL prices.quantity to a decimal-capable type without dropping data.
  5. Keep sqlite tests compatible with GORM AutoMigrate.
  6. Regenerate Swagger with swag init -g main.go.
  7. Run focused tests, then go test ./..., go vet ./..., and update this plan with results.

Risks and Edge Cases

  • GORM may not safely narrow or alter an existing PostgreSQL integer column through AutoMigrate; use an explicit guarded migration.
  • Changing public JSON schema from integer to number needs coordinated mobile client changes.
  • float64 is acceptable for quantity, but not a broader money precision fix.
  • Existing custom units remain string-based and should not be reinterpreted as part of this change.

Rollback Plan

Before production deploy, rollback is a normal code revert. After a production schema migration to a wider decimal type, do not automatically narrow prices.quantity back to integer; old integer-only app code can still write integer-compatible values into a decimal column.

Open Questions

  • Use PostgreSQL double precision to match Go float64, or numeric for stricter stored decimal semantics?
  • Should backend add kom as an alias for pcs, or should the mobile app canonicalize count units to pcs only?

Approval Gate

Implementation must not start until this plan is explicitly approved. After approval, backend changes should stay scoped to decimal price quantity support, migration handling, tests, and generated API docs.

Implementation Results

  • models.PriceCreateDTO.Quantity and models.Price.Quantity now use float64.
  • PriceCreateDTO.Quantity is required and must be greater than zero, so 0.5 is accepted while 0 is rejected.
  • CalculateIngredientCost now accepts decimal price quantities and keeps the existing unit conversion behavior.
  • A guarded PostgreSQL startup migration changes existing prices.quantity columns to double precision before AutoMigrate runs.
  • SQLite controller tests continue to rely on GORM AutoMigrate for the test schema.
  • Swagger was regenerated after the model change, and price quantity is now documented as a JSON number.
  • The kom count-unit alias remains out of scope for this backend change.

Known Limitations and Follow-Up

  • This is a quantity precision change, not a broader money precision change; price values still use the existing float64 model.
  • The production database migration has not been smoke-tested against live Postgres in this implementation pass.
  • Mobile client updates should send canonical units and decimal JSON numbers for quantity.
