Implementation Plan: JWT Revocation on Password Change

Approval required before implementation

Task Summary

Fix the security scan finding BV-AUTH-001: changing a password updates the bcrypt hash, but already issued JWTs remain valid until their original 24-hour expiration. The fix should invalidate tokens issued before the latest password change while preserving normal login and workspace behavior.

Current Behavior

  • controllers/auth.go issues JWTs with userID, ExpiresAt, IssuedAt, and Subject.
  • middleware/auth.go validates signature, signing method, and registered claims, then sets userID in Gin context.
  • controllers/profile.go verifies the current password and saves only the new password hash.
  • models/user.go has no token version, password-changed timestamp, session epoch, or revocation field.
  • database.ConnectDatabase() runs AutoMigrate(&models.User{}) on startup, so adding a nullable/simple user column follows the repo's current migration style.

Desired Behavior

  • Tokens issued before the user's latest password change must be rejected by protected API middleware.
  • Fresh login tokens issued after password change must continue to work.
  • Existing users should not be locked out by the migration.
  • Token validation errors should remain generic and should not leak account state.

Proposed Approach

Use a monotonic TokenVersion integer on User instead of timestamp comparison. This is simpler than time-based revocation because it avoids clock precision and equality edge cases. JWTs carry the version at login; password change increments the stored version; middleware compares the token version to the current stored value.

Why token version

Works with GORM auto-migration, has deterministic tests, and does not depend on sub-second DB timestamp behavior.

Compatibility

Default zero version allows existing users to keep working until their next password change or login cycle.

Implementation Steps

  1. Add TokenVersion uint `json:"-" gorm:"not null;default:0"` to models.User.
  2. Add TokenVersion uint `json:"tokenVersion"` to both auth claim structs, or consolidate claim definition if that is low-risk.
  3. During login, include user.TokenVersion in the JWT claims.
  4. In JWTMiddleware, after signature/expiry validation, load the user by claims.UserID and compare claims.TokenVersion to user.TokenVersion.
  5. Reject missing users, stale versions, and DB errors with generic unauthorized/internal responses as appropriate.
  6. In ChangePassword, update the password hash and increment token_version atomically enough for this single-row update.
  7. Add focused tests for stale-token rejection and post-change version increment.
  8. Run formatting and tests.
  9. Update this HTML plan with actual changes and checks after implementation.

Data, API, Auth, and Deployment Impact

  • Database: adds one non-sensitive user column via GORM auto-migration.
  • JWT contract: new tokens include an additional private claim. Existing tokens without the claim will read as version zero.
  • Auth behavior: after a password change, all tokens with the old version are rejected.
  • Deployment: no manual SQL migration is planned unless tests show GORM default handling is insufficient.
  • Performance: JWT middleware will add one user lookup per protected request. This is acceptable for a small API but should be noted.

Manual QA Checklist

  • Register or use a test user.
  • Log in and save token A.
  • Change password using token A.
  • Confirm token A is rejected on a protected route after password change.
  • Log in with the new password and confirm token B works.
  • Confirm workspace discovery and normal protected routes still behave correctly with token B.

Risks and Edge Cases

  • Extra DB read on every authenticated request may become a performance concern later.
  • Existing tokens without tokenVersion should be treated carefully; with default zero they remain valid until the first password change increments the stored version.
  • If a user row is soft-deleted, middleware should not keep accepting tokens for it. The user lookup should respect GORM soft deletes.
  • Concurrent password changes should not accidentally keep the same token version. Use an increment expression rather than read-modify-write if practical.

Rollback Plan

Revert the code changes and redeploy the previous backend image. The added column can remain unused in the database; it is non-sensitive and backward-compatible. If a manual cleanup is desired later, remove the column in a separate explicit migration after confirming no running version depends on it.

Open Questions

  • Should password change revoke all tokens only, or should future logout/session-management support also use the same token version?
  • Is one user lookup per authenticated request acceptable for current production traffic, or should this become a cached/session-backed design later?
  • Should changing username or future MFA/security settings also increment token_version?

  • Logout and multi-device session management remain out of scope for this fix.
