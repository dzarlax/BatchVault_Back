Backend Plan: Ingredient Unit Contract

Repo: D:\Projects\Code\Personal\jerky-vault-back. Branch: codex/backend-ingredient-unit-contract, based on origin/main.

Goal

Make backend the source of truth for purchase/recipe unit choices. Clients should receive canonical allowed_units and default_unit for each workspace ingredient instead of guessing from ingredient names or categories.

Current Behavior

  • models.Ingredient has type and name.
  • models.WorkspaceIngredient has workspace metadata such as alias and category, plus transient latest_price.
  • models.PriceCreateDTO accepts raw unit.
  • utils.CalculateIngredientCost already knows dimensions for kg/g, l/ml, pcs, and custom same-unit values.

Desired API Shape

{
  "id": 123,
  "workspace_id": 1,
  "ingredient_id": 45,
  "category": "spice",
  "unit_profile": "fine_mass",
  "default_unit": "g",
  "allowed_units": ["g", "kg"],
  "ingredient": { "id": 45, "name": "Salt", "type": "spice" },
  "latest_price": { "unit": "kg", "quantity": 2.5, "price": 650 }
}

Recommended canonical units: kg, g, l, ml, pcs, hh. Labels remain a client/localization concern.

Implementation Steps

  1. Create a backend unit catalog in constants, with profiles: mass, fine_mass, volume, count, time.
  2. Add a resolver that returns unit_profile, default_unit, and allowed_units from ingredient.type/workspace_ingredients.category without DB schema changes.
  3. Expose resolved fields in GET /api/workspace-ingredients and returned workspace ingredient objects.
  4. Do not add persisted overrides in this pass; there is no product UI for editing them yet.
  5. Keep price/recipe writes permissive. Strict validation should wait until clients consume allowed_units.
  6. Regenerate Swagger docs after response changes.
